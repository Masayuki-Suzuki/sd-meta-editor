# ADR-0003: バッチ処理を v1 に導入する（プリセット適用限定）

**Status:** Accepted
**Date:** 2026-11-12

## Context

当初はバッチ処理を v2 送りとする案だった。しかし本ツールの主用途が「編集」ではなく「公開前の削除」であると確定した（ADR-0002 の Context を参照）ため、前提が変わった。

「公開前にフォルダ内の画像からまとめてメタデータを消す」は極めて自然な行動であり、1 枚ずつの処理では実用にならない。

## Decision

- v1 からフォルダ／複数ファイルの一括処理を提供する
- 操作は**削除プリセットの適用のみ**とする。個別のテキスト編集は単一ファイルモード専用
- プリセットは**複数選択可のチェックボックス式**とする（「全削除」のみ排他）
- 進捗表示・キャンセル・部分失敗サマリを必須とする
- プリセットが参照するフィールドが存在しないファイルは**エラーにせず無視**（no-op）する

## Rationale（却下案の記録）

| 案 | 却下理由 |
|---|---|
| v2 送り | 主用途が削除である以上、1 枚ずつでは実用にならない |
| CLI のみで提供 | 実装は最小だが GUI ユーザーに届かない。ただし CLI でも同機能を提供すること自体は併せて行う |
| バッチでも個別編集を可能にする | ファイルごとに内容が異なるため UI が破綻する。プリセット適用に限定するのが妥当 |

## Consequences

**得られるもの**

- 主用途に v1 で応えられる
- CLI と GUI が同一のプリセット定義を共有できる

**受け入れるリスク**

- プリセットは**ツール非依存の抽象レイヤ**を前提にせざるを得ない。正規フィールドモデル（要件定義書 FR-3）の実装が必須となる
- 進捗・キャンセル・部分失敗の設計コストが増える

## 本決定から派生する設計制約

### C-8. プリセットは正規フィールドのみを参照する

プリセットがツール固有のキー名を直接参照してはならない。ツール別アダプタが正規フィールドへ写像し、プリセットはその抽象だけを扱う。これによりツールが増えてもプリセット定義は変更不要となる。

### C-9. 一括処理は部分失敗を許容する

1 ファイルの失敗で全体を中断しない。失敗したファイルと理由を収集し、完了後にサマリとして提示する。

## 再検討のトリガー

- 一括処理に対して「ファイルごとに異なる編集をしたい」という要求が主流になった場合
