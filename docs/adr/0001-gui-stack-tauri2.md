# ADR-0001: GUI スタックに Tauri 2 を採用する

**Status:** Accepted
**Date:** 2026-11-12

## Context

本アプリの本質は「画像コンテナのバイト列を無劣化で書き換えること」であり、UI 層は薄い。一方でユーザー体験上の中核機能は**長文プロンプトの複数行テキスト編集**であり、既存類似アプリの最大の不満点（入力が受け付けられない／Save が無反応）もここに集中している。

したがって GUI スタック選定の判断基準は以下の順とする。

1. テキスト編集品質と入力応答性
2. 3 OS 配布の現実性
3. 配布サイズ・起動速度

## Decision

**Rust コアライブラリ + Tauri 2 シェル**を採用する。フロントエンドは **TypeScript**。

```
crates/sdmeta-core/   pure Rust。パース・編集・ロスレス書き出し。GUI 非依存・単体テスト対象
crates/sdmeta-cli/    バッチ処理・調査用 CLI（同一コアを利用）
app/                  Tauri 2 シェル（src-tauri + web frontend）
```

## Rationale（却下案の記録）

| 案 | 却下理由 |
|---|---|
| **egui / eframe** | 複数行テキスト編集と IME 処理が弱い。本アプリの中核機能であり、かつ既存アプリの不満点そのものなので看過できない。単一バイナリの利点は代償に見合わない |
| **C# + Avalonia** | Rust でコアを書ける前提では採用の積極的理由がない。ランタイム依存が増えるだけ |
| **Electron + TypeScript** | 配布サイズ 100MB 超、常駐メモリとレンダリングコストが過大。「軽快さ」を売りにするアプリとして自己矛盾する |
| **Slint** | 設計は妥当だがエコシステムが薄く、画像 I/O・OS 統合周りで自前実装が増える |
| **Flutter** | 画像メタデータ系ライブラリが貧弱で Rust への FFI が必須。ならば Rust 直で良い |

## Consequences

**得られるもの**

- テキスト編集・IME・アクセシビリティを OS 標準 WebView（WKWebView / WebView2 / WebKitGTK）に委譲でき、自前実装ゼロで最高品質
- バイナリ 10MB 前後、起動 100ms 台が狙える
- コアが UI 非依存なので、将来 GUI を差し替えても資産が残る。CLI が副産物として得られる
- D&D・ネイティブファイルダイアログ・設定永続化・自動更新が公式プラグインで揃う

**受け入れるリスク**

- **Linux は WebKitGTK 依存**（`webkit2gtk-4.1`）。ディストリ差で描画バグが出る。既知回避として NVIDIA + 一部環境で `WEBKIT_DISABLE_DMABUF_RENDERER=1` が必要になるケースがある → AppImage に起動ラッパを同梱し README に明記する
- WebView のバージョン差による CSS/JS 挙動差 → フロントは保守的な機能だけ使い、3 OS で CI スクリーンショット比較を行う
- IPC 境界が存在する → 大きなバイナリを JSON で跨がせると性能が破綻する（C-3 参照）

## 本決定から派生する設計制約

以下は**仕様として確定**とする。守らない場合、既存アプリと同じ症状を再現する。

### C-1. CPU 処理を絶対にメインスレッドに置かない

Tauri の非 async コマンドはメインスレッドで実行される。これが最大のフリーズ要因。デコード・解析・書き出しはすべて `spawn_blocking` / rayon 側に逃がし、コマンドは `async` で宣言する。

### C-2. キー入力で IPC を発生させない

プロンプト本文のステートはフロントエンド内に閉じる。バックエンドへの送信は「保存」「再解析」などの明示操作時のみ。**デバウンス付きの自動同期も入れない。**

### C-3. プレビュー画像を IPC で運ばない

base64 で JSON に載せるのは禁止。Rust 側に**カスタム URI スキーム**を登録し、縮小済みサムネイルをバイト列でストリーム配信する。JPEG は DCT スケール（1/2・1/4・1/8）で高速縮小する。原寸表示が必要な場面のみ `asset:` プロトコル + `convertFileSrc()` を使い、WebView のネイティブデコーダに任せる。

### C-4. ドラッグ&ドロップは Tauri のネイティブイベントを使う

WebView 内の HTML5 drag-drop では `File` オブジェクトから実ファイルパスが取れない。`onDragDropEvent`（`@tauri-apps/api/webview`）でパスを受け取る。HTML5 側の D&D を使う場合は `dragDropEnabled: false` が必要で**両者は排他**。

### C-5. capability / permission は最小権限で設計する

`capabilities/*.json` に `dialog:allow-open`、`fs` の read/write、`assetProtocol` スコープを必要最小限で宣言する。

### C-6. エラーは必ず UI に到達させる

`Result` を `Err` で返してフロントで握り潰す経路を作らない。トースト表示とログファイル出力を二重化する。「Save を押しても無反応」は例外の沈黙が原因であることが多い。

### C-7. macOS universal ビルド

`tauri build --target universal-apple-darwin` を CI に組み込む。

## フロントエンドフレームワーク（付帯事項）

**React 19 + TypeScript + Vite** を採用する。開発者の既存知見を活かし開発速度を優先する。ただし C-2 を守るため以下を規律として明文化する。

- プロンプトの `<textarea>` は **uncontrolled（`ref` 管理）**。`value` + `onChange` で毎打鍵再レンダする構成を禁止
- グローバルステートはセレクタ購読型（Zustand 等）を使い、**プロンプト本文はそこに入れない**
- メタデータ一覧の各行は `memo` 化し、1 行のトグルが全体再レンダを起こさないこと

代替として Svelte 5（runes）は細粒度リアクティビティによりこの規律自体が不要になるが、学習コストを考慮し React を採用する。上記 3 点を守れば性能目標は達成可能と判断した。

## 再検討のトリガー

- Linux の WebKitGTK 起因の描画不具合が回避不能なレベルで頻発した場合 → Slint / egui を再評価
- テキスト編集以外に高頻度の重い描画要件（大量画像のグリッド表示など）が追加された場合 → ネイティブ描画系を再評価
